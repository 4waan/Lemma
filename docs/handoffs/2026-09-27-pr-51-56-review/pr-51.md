### Findings

1. **Docs, wrong figure.** `docs/warranty-registry-review.md:44` (and the description) say "12,472 bytes of runtime code". The current build is 11,108 bytes of runtime code and 12,408 bytes of initcode (`forge build --sizes`, and the artifact's `deployedBytecode`). The figure is a stale initcode size labeled as runtime. Re-measure and label it.
2. **Design limitation to guard before deployment (backlog item 20, decision D2).** `_resolutions` is keyed by `resolutionId` alone (`ResolutionWarrantyRegistry.sol:149`), a voucher is valid when signed by the provider of *its own* `releaseDigest`, and the first activation wins (`:380`). So any registered provider can activate any resolution id under its own release before Lemma's activator does. The buyer's real warranty then never activates, and if both releases share the evaluator key, the outcome finalizes under the wrong release: the engine records it against the wrong digest, and a FAILED credit sits behind the attacker's `claimHash`, out of the buyer's reach. It needs a registered provider and a resolution id learned before the (up to 300 s) activation delay, so it is not a testnet blocker, but the server should refuse to treat a foreign activation as its own (see the #55 review, activator finding), and the id space should become per release before mainnet (D2).
3. **Follow-ups the backlog already tracks, confirmed in the code:** no retry for `EngineRecordFailed` (`:612`, `:620`; item 21, D3); no provider or evaluator rotation, only `deactivateRelease` plus a new digest (item 22, D4); no sweep of USDC sent directly to the contract, so `balance - (available + reserved + credits)` is stuck for good (item 23, D5); no Slither step and no submodule alerts in CI (items 24, 25).
4. **Note for the runbook.** `withdrawCredit` (`:487`) pays only the address committed in `claimHash`. If USDC blocklists that address, the credit is stuck, because the buyer cannot choose another. That is one more reason for the refund address to be a fresh one the buyer controls (backlog item 6).

Things I checked and found sound: pause arithmetic (`_claimDeadline` moves every running deadline by the seconds paused since activation, finalization allowed at the deadline and expiry only after it); `depositBond` fails closed on a fee-on-transfer amount and refuses deactivated releases; `withdrawUnreservedBond` and `withdrawCredit` work while paused; effects before transfers everywhere; the engine call runs last under the reentrancy lock with a fixed 300,000 gas budget and a gas floor (`:133`) so a relayer cannot starve it; events carry no buyer or payer; `renounceOwnership` is disabled; `SignatureChecker` accepts ERC-1271 signers; the deploy script refuses a wrong chain, a wrong USDC, zero roles and a key that does not match `DEPLOYER_ADDRESS`, and the record holds no secret.
