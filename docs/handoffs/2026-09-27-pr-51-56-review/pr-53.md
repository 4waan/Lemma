### Findings

1. **Should fix before merge (privacy).** `GET /api/v1/resolutions/:id` returns `createdAt` at millisecond precision (`packages/core/src/read.ts:136`, `apps/server/src/service.ts:262`) together with `terms.payTo` and `terms.amount`. `createdAt` is set in `prepare`, seconds before the facilitator sends the USDC transfer, so anyone holding a resolution id can find the payer's wallet on chain: the linkage `derivePaymentNonce` exists to prevent. #55 already replaces it with the UTC day (`createdOn`), and its description calls the same issue a blocker its reviewers found. Merge #53 with #55, or backport that read-model change.
2. **Should fix before merge (validation).** `apps/server/src/payments/handler.ts:51` accepts a `validBefore` of up to 15 digits and `:98` turns it into a `Date`; for 13 digits or more the result is an Invalid Date, and the "no longer than quoted" check at `:136` compares `NaN`, which is never greater, so the refusal is skipped. x402 accepts such a value. On Postgres the store then throws on `toISOString()` and the purchase fails closed as `UNAVAILABLE`; on `MemoryStore` the row is stored with a `NaN` window that `listUnsettled` never lists, so a settlement whose commit failed is unrecoverable. One-line fix: return `undefined` from `authorizationOf` when `Number.isFinite(validBefore.getTime())` is false (or cap the regex at 11 digits), and add the case to the window test.
